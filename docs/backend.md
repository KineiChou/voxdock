# Backend integration

`@voxdock/backend` connects a bridge to one configured HTTP(S) base URL. It never follows redirects or accepts a callback URL from a model. Request bodies use the published schemas; responses are capped at 64 KiB and have a bounded timeout. Authentication uses a dedicated bearer token. Transport errors and timeouts leave business acceptance unknown: do not tell the caller that a job was rejected or completed merely because a request failed.

Create `BackendClient({ baseUrl, requestToken, eventSigningKey, timeoutMs?, fetch?, now? })`. The injected fetch and clock support offline tests. Call `context(call, principalRef, 'before_dial')` before reserving platform side effects, then call it again with `before_greeting` immediately before speaking. The response envelope is `{ call_id, context_ref, context }`, where `context` follows `BackendContext`. Both identifiers must match. An obsolete context means do not start the intended call or deliver its stale opening. The client returns the flag; the coordinator performs cancellation or a factual fallback.

`delegate(payload)` sends a durable delegation identity and context revision. The result must identify the same call, delegation and context revision. The result revision independently increases for business updates. Retrying a timed-out delegation must reuse its identity and revision; the backend must persist acceptance before returning a receipt.

`deliverEvent(event)` signs `timestamp + '.' + raw JSON bytes` with HMAC-SHA256. Headers are `x-voxdock-timestamp` (Unix seconds) and `x-voxdock-signature` (lowercase hexadecimal). Each retry uses the same event and a fresh timestamp. The backend verifies signatures with constant-time comparison and a five-minute clock window. Its event ID ledger acknowledges identical replay and rejects changed content. Keep host clocks synchronized.

`OutboxWorker(client, store, deadlineHours?).runOnce(limit?)` delivers due core events and acknowledges or schedules their retry. Calls are serialized across worker instances in one process. Deploy one bridge process per SQLite database; this worker is not a multiprocess lease implementation. It never starts a phone call. The application owns scheduling and shutdown.

## Independent example

The example defaults to simulation mode. An opt-in OpenAI mode provides real text answers; neither mode is a coding agent or a business executor. It persists accepted `example_job` receipts in SQLite; jobs survive a backend restart and call termination. It does not execute Codex. Simulated completion requires an explicit authenticated request. `GET /simulation/jobs` shows their durable status. Context references beginning with `obsolete:` exercise stale-notification handling. Completed simulations create a durable callback to the configured bridge; a phone hangup does not cancel the job.

Run from the workspace with `pnpm --filter @voxdock/example-backend start`. It defaults to `127.0.0.1:8090`; `EXAMPLE_BACKEND_HOST` can bind a private container interface. Set `BACKEND_REQUEST_TOKEN_FILE` and `BACKEND_EVENT_SIGNING_KEY_FILE` to secret files, or provide `BACKEND_REQUEST_TOKEN` and `BACKEND_EVENT_SIGNING_KEY` through the environment. File values take precedence. Optional settings are `EXAMPLE_BACKEND_PORT` and `EXAMPLE_BACKEND_DATABASE`. Secrets and request payloads are not logged. Use a service manager or secret store for production credentials.

The example exposes authenticated `POST /voice/v1/context`, `/voice/v1/delegations`, `/voice/v1/events`, and `GET /simulation/jobs`. Event signatures cover the unmodified request body. Call state merges by increasing revision; out-of-order events cannot undo later state. Received event bodies and delegation transcripts are hashed for deduplication. Simulation mode does not persist plaintext transcripts; OpenAI mode temporarily persists queued input as described below. SQLite uses WAL and full synchronization; apply the same local-filesystem and consistent-backup rules as the bridge.

## Simulated completion and callbacks

Query `GET /simulation/jobs` for a job ID and its current context revision (the job list names this field `revision`). Explicitly complete that version with authenticated `POST /simulation/jobs/{url-encoded-job-id}/complete` and JSON `{ "context_revision": 1 }`. The response is labeled `simulation: true`; it claims only completion of the simulated example. Repeating this request returns the same durable result. A stale context revision conflicts. A corrected delegation reopens the same job as accepted, supersedes pending callbacks from the old context, and assigns a new result revision without resetting the result counter.

Configure `EXAMPLE_BRIDGE_BASE_URL_FILE` with a file containing the trusted bridge HTTP(S) base URL, or use `EXAMPLE_BRIDGE_BASE_URL`. Set `VOXDOCK_CONTROL_TOKEN_FILE` to the bridge control-token file. The example CLI drains pending callbacks at startup and every second. Requests cannot supply a callback URL. Without callback configuration, completions remain durable and pending.

Callbacks use `POST /v1/calls/{call_id}/delegations/{delegation_id}/results`, bearer authentication, a bounded timeout and response size, and no redirects. The completion and callback commit in one transaction before delivery. Retries retain the exact result ID and body, back off up to one hour, and stop 24 hours after completion. `accepted: true` is persisted even when `playback_status` is `not_played`; a hung-up call must not cause a replacement call. If the response is lost after acceptance, the receiver's result ID deduplication prevents repeat work.

`GET /simulation/callbacks` reports pending, accepted, superseded or failed delivery. `POST /simulation/callbacks/deliver` performs an authenticated immediate drain; it does not bypass backoff or the deadline. The programmatic server factory exposes `app.deliverCallbacks()` for explicit scheduling and offline tests. The CLI owns periodic scheduling and aborts in-flight delivery before closing SQLite. The example uses a single process and does not implement distributed callback leases.

## OpenAI text forwarding

Set `EXAMPLE_BACKEND_MODE=openai`, `OPENAI_API_KEY_FILE` (or `OPENAI_API_KEY`), and optionally `OPENAI_MODEL` (default `gpt-5.6-sol`). The operator may mount the same managed API-key file used by Live. The key stays in the backend process; delegation requests cannot supply keys, provider URLs, or model settings. `EXAMPLE_BACKEND_LANGUAGE` (default `en`, for example `zh-CN`) sets the initial Live context language; model instructions ask it to match the caller's language. Simulation remains the default mode. Use a separate database per mode; changing modes against an existing database is unsupported.

This calls the fixed OpenAI Responses endpoint with `store:false`, low reasoning effort, and at most 1024 output tokens. It offers text assistance only: no tools, shell, file access, browsing, code execution, or long-term memory. The supplied transcript fragments, including Live's normal partial fragments, are ordered by sequence and forwarded with their speaker labels. Empty user input and input over 32 KiB after JSON encoding are rejected before acceptance. The HTTP request body remains capped at 64 KiB. The model is asked to clarify incomplete requests and keep spoken replies concise in the caller's language.

Acceptance and the input queue commit together before the HTTP receipt returns; they do not wait for the provider. The CLI starts a single worker, checks for work every 250 ms, and continues using the existing durable callback worker. Programmatic callers schedule `app.runModelWork()` and `app.deliverCallbacks()` themselves. Run exactly one backend process per SQLite database. Concurrent worker invocations in one process share the same active operation.

Provider calls have a 60-second timeout, no redirects, and a 64 KiB response limit. Only a completed response with nonempty assistant output text of at most 4000 characters becomes a completed result. API errors, empty/incomplete/oversized output, timeout, or shutdown produce a failed result that does not claim the provider rejected or never processed the request. There is no automatic paid-request retry. On restart, queued work resumes; previously running work becomes failed with an unknown-outcome explanation. A duplicate delegation/revision returns its original acceptance and cannot resubmit provider work. A newer revision supersedes queued input and pending old callbacks; an older in-flight result is discarded. A new revision is a new authorized request and may incur another provider charge.

Model completions and failures use the same transactional completion/callback ledger as simulations. Callback retries never repeat the model request. An ended call keeps the result durable and cannot trigger redial. All `/simulation/*` routes return 404 in OpenAI mode, including manual simulated completion. Provider errors, credentials, and transcripts are never logged.

The CLI uses a private file-creation mask (`0077`); keep its database, WAL, and backups in an operator-only directory. Programmatic callers must provide equivalent permissions. Queued/running transcript input is plaintext in that private SQLite database and is cleared upon terminal completion or replacement by a newer revision. SQLite secure deletion and terminal WAL checkpointing reduce live-file remnants; filesystem snapshots and backups may retain older input and require the operator's own retention policy. Result text remains in the completion and callback ledgers for durable delivery/deduplication and may contain caller information. There is no automatic ledger expiry: retain and delete the whole database according to your private-data policy after pending delivery and replay protection are no longer needed. OpenAI receives the forwarded text; `store:false` is not a claim of zero provider retention.
