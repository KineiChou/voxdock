# Call runtime

`createRuntime({ config, store, configDirectory? })` returns `readyChannels`, `onCallCreated`, `onEnd`, `onResult`, and `close`. The HTTP layer durably creates outbound calls, then invokes `onCallCreated`; it persists fresh eligible backend results before invoking `onResult`. The coordinator pumps the signed event outbox once a second when a backend is configured, with cancellation and no new database writes after shutdown. Shutdown must await runtime close before closing SQLite.

Telegram startup connects an existing session in a separate Node process. The child uses `--import tsx`, owns the native addon and account client, and receives fixed configuration paths through IPC. Native crashes cannot crash the HTTP process. Startup never prompts for login. Initialization failure leaves Telegram unavailable. IPC caps outstanding requests at 32, verifies audio frame sizes, bounds operations to 15 seconds, and terminates an unhealthy worker. Account setup is explicitly invoked through the console, API or CLI and temporarily owns the stopped runtime. Telegram supports SDK QR rotation/migration/two-step authentication and phone-code fallback. A passive observer verifies a separate receiving account by exact private message code or a fresh incoming call, then requires operator confirmation. Verification never starts native audio or Live. The private `<sessionFile>.peers.json` contains only confirmed account-bound user IDs/access hashes; startup restores them to the SDK entity cache because StringSession does not serialize entity metadata. Back it up together with its login session. Explicit Telegram disconnect removes both local files.

The parent maps configured target IDs to stable peer IDs from their configured environment variables. Call requests cannot supply platform peers, credential paths or backend addresses. Incoming offers require the fixed caller match and a durable global-capacity reservation before acceptance. Incoming business references are `context_ref=inbound:<target-id>` and `correlation_ref=incoming:<provider-call-ref>`; the configured backend must resolve those references. Foreign callers are rejected before any Live session exists.

Both directions check fresh business context before a platform side effect. Obsolete context cancels the attempt. Once the platform is connected and media ready, the runtime starts one Live session, refreshes context again and appends one opening instruction. Context data is capped at 8,000 UTF-8 bytes for this briefing, then split into bounded appends. An obsolete refresh produces a factual stale-notification opening instead of old task details. Append acknowledgments are not evidence the caller heard the message.

Audio has bounded 500 ms PCM queues and shared monotonic pacing. Ordinary late ticks advance the nominal frame deadline instead of shifting the sample clock. After a whole slot is missed, pacing restarts from the current time; each tick emits at most one frame per direction. Live receives continuous 20 ms input frames, including silence during quiet or DTX intervals; Telegram receives paced 10 ms frames. Two persistent FFmpeg processes convert 48 kHz Telegram PCM to/from Live's 24 kHz PCM. FFmpeg must be installed. Queue overflow, failed write, worker exit, or Live fault initiates cleanup. Audio failures retain a fixed boundary code in call state: `audio_input_overflow`, `audio_output_overflow`, `audio_input_resampler_failed`, `audio_output_resampler_failed`, `audio_live_write_failed`, `audio_phone_write_failed`, or `audio_phone_write_pending` (the previous write did not settle before the next frame). Resampler backpressure is included in its direction’s resampler-failure code. These codes contain no audio, provider error text, or caller data. A gap in received audio alone does not prove disconnection. Once connected, the duration limit stays fixed. With the smaller of 30 seconds or half the maximum duration remaining, the runtime attempts one brief warning instruction in the current conversation language if this call is still connected and Live is ready with its opening appended. It skips unavailable Live sessions, never retries a rejected warning, and clears the warning timer on termination. The warning cannot delay the hard deadline, and its append is not proof of playback. The call duration and ringing deadlines also end the session; ambiguous platform outcomes remain `uncertain`, retaining capacity and preventing redial.

Transcript fragments remain marked `final:false`: Live delta events do not prove transcript finality. The runtime deduplicates provider transcript event IDs, assigns monotonic transcript context revisions, and sends partial delegation snapshots through the configured backend. Late fragments at or before a delegation offset update that delegation's revision. This revision namespace is independent of the business context snapshot revision and backend result revision. Synchronous backend receipts are persisted before commentary. Async results are rechecked against the current stored delegation revision and connected Live state immediately before each spoken append. A backend timeout means acceptance is unknown; there is no automatic request replay. Closing the call does not cancel the backend job.

Official final Live usage settles the durable reservation. Missing final usage retains an incomplete reservation. Runtime teardown bounds platform cleanup and Live finalization and ignores late callbacks after disposal. Audio is never stored. Transcripts follow the store's configured retention behavior; bounded in-memory fragments still support active delegation when transcript persistence is disabled.

The default runtime has Telegram and WhatsApp drivers; each channel remains unavailable until its configured account transport passes startup checks. Dependency injection supports offline lifecycle tests without loading native code or contacting accounts/models. Tests exercise outbound context/greeting/delegation/result flow, durable inbound admission, foreign caller rejection, obsolete context cancellation, continuous input, final usage and worker-failure uncertainty. These are coordinator tests with mocked platform and Live transports, not proof of actual phone or paid-model operation.


## WhatsApp account and media binding

WhatsApp `account_ref` is the exact WaCalls session ID returned by `GET /api/sessions`, not a display name or an arbitrary account label. Pair the account using the [upstream WaCalls account UI](https://github.com/JotaDev66/WaCalls/tree/edeb31f0427aba896639db503153b777a405eccf); session creation/pairing and QR display are operator actions outside the runtime. The runtime neither creates accounts nor logs QR data. It requires that session to be paired and `open`, derives the caller phone from its device JID and rejects a target matching the caller account. The target environment value is a personal phone-number JID (`digits@s.whatsapp.net`) or a canonical international phone number. Account identifiers are never taken from call requests.

Before publishing readiness, the driver opens SSE, verifies the account snapshot and requires an empty initial upstream call list. Existing upstream calls require operator reconciliation. HTTP and media origins must be trusted private service configuration; the unpatched control routes have no authentication. Session changes, invalid events, disconnected SSE or a missing 45-second transport heartbeat remove readiness and preserve uncertain active state; no automatic stream reconnection or redial occurs.

Incoming callers are matched against the configured target. A raw LID cannot be converted into a phone by stripping its suffix. If patched upstream supplies `peer_phone_jid` from its account's stored whatsmeow LID-to-phone mapping, that verified mapping can authorize a bare or device-qualified LID (`number@lid` or `number:device@lid`); absent, mismatched or malformed mappings remain rejected. Unresolved modern WhatsApp identities remain a real-account compatibility limit. The coordinator reserves the shared durable call slot before the adapter sends accept. HTTP acceptance and upstream optimistic ringing never imply connected: only a matching session/call `connected` event starts authenticated call-bound media. The shared runtime supplies continuous 16 kHz mono PCM16LE in 20 ms frames, with no resampling for WhatsApp.

The bounded Go termination patch distinguishes `termination:acknowledged`, `remote` and `unconfirmed`. The driver accepts the first two as platform termination evidence. An acknowledged terminate stanza is a signaling receipt, not proof of the remote handset's UI. Legacy local-ended events and HTTP 204 alone cannot prove hangup because the original upstream discarded asynchronous signaling errors; those leave the call uncertain. No fabricated terminal state is used to free capacity.

The media WebSocket and signaling event stream have independent delivery order. Unexpected media closure or startup failure stops that call's audio and reports it as uncertain while retaining signaling. The coordinator attempts bounded termination; a missing-call response alone does not release capacity. A later matching `remote` or `acknowledged` event can settle the call and permit the next one. Duplicate or stale media callbacks cannot affect a new call. Signaling loss, heartbeat failure and account changes still invalidate the channel and require operator recovery.

Isolated WhatsApp adapter tests exercise readiness/account checks, incoming admission/identity mapping, actual connected-event gating, PCM routing, legacy uncertainty and patched termination evidence. Coordinator tests also exercise the shared lifecycle and duration warning/deadline. Real-device evidence now includes account pairing and a two-minute outgoing Live/Sol conversation; incoming acceptance and normal handset termination remain open. See [acceptance](acceptance.md).
